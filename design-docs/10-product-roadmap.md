## 1. 背景与目标

### 1.1 起点

Mora MVP（YS-4）已完成从需求规范到容器化交付的完整闭环：块级文档 + Markdown 双向可逆、多工作区隔离与无限级目录、不可改写版本历史与 Diff 回滚、显式优先的 RBAC 权限继承、BM25 全文 + 向量 RAG 混合检索、实时协同编辑（presence / cursor / 并发降级）、评论与审阅、MCP 工具层、审计与限流，Docker Compose 一键拉起、默认不出网。wiki→mora 全栈品牌标识迁移亦已完成（见 `08-brand-naming-spec.md`）。

在此基础上，产品进入**功能完善与体验迭代期**。本路线图回答一个问题：**MVP 之后，按什么顺序把哪些能力补齐与拓展，才能让 Mora 在「企业内部文档协作 + 个人知识管理」两类场景上真正可用、好用、有竞争力。**

### 1.2 目标

- **守住核心承诺**：协同知识库的产品底线是「多人实时协作」与「权限可控检索」。M1~M2 优先修复 CRDT 实时协同降级问题，让「协同」二字名副其实。
- **补齐内容流转闭环**：让存量知识能低成本迁入（导入/模板），让信息能被高效发现与组织（仪表盘/通知/标签），降低首次使用与日常使用的摩擦。
- **建立可维护的体验基线**：落地设计语言令牌体系，使后续迭代不依赖硬编码裸色、换色与主题可控。
- **为增长打地基**：外部分享、AI 写作助手、画板等 P2 方向，复用现有 RAG / MCP 能力栈，避免重复建设。

### 1.3 路线图原则

1. **增量优先**：所有设计在 Mora 现有「工作空间 / 目录 / 文档 / 块 / 版本 / RBAC / 检索 / 协同 / MCP / 审计」模型上做增量，不另起炉灶；涉及架构扩展处标注「需技术评审」。
2. **RBAC 全链路硬约束**：任何新增内容入口（导入、分享、AI 工具）都必须复用同一权限引擎，无权资源存在性不泄露。
3. **私有化不变**：所有迭代保持自托管、默认不出网；新增能力优先本地化推理（复用 TEI/Ollama），不引入强制出网依赖。
4. **P0 阻塞核心承诺，P1 补齐体验，P2 拓展边界**：优先级服从「先让承诺成立，再让体验顺滑，最后拓展场景」。

## 3. 各 R-item 详述

### R1 设计语言规范落地（P0 · YS-54 · M1~M2）

**问题**：前端使用 shadcn/ui 默认令牌，未建立品牌设计语言——品牌色为纯灰阶（chroma=0）、无字体系统（`@tailwindcss/typography` 未安装导致编辑器 `prose` 无效）、7+ 处硬编码裸色、favicon 仍为 `vite.svg`、无可见主题切换 UI。

**目标**：将前端从「能用的默认模板」升级为「有品牌设计语言的产品」，建立可维护的令牌体系，使换色成本仅改 `index.css` 一处。

**范围**：
1. 设计令牌与字体基础设施：品牌主色（靛蓝 Indigo，oklch hue 265）+ 语义状态色（success/warning/info）令牌替换；字体系统（Inter + JetBrains Mono + Noto Sans SC）；安装 Typography 插件。
2. 硬编码色清理 + 品牌标识 + 主题切换：7 处裸色 → 语义令牌；mora Logo + favicon；ThemeToggle 组件。
3. 基础组件补全与排版打磨：EmptyState / LoadingState / StatusBadge / Toast；替换内联空态与反馈文案。

**落地子任务**：YS-54（父）→ 令牌字体 / 色清理+品牌标识 / 组件补全。

**与 Mora 现有能力的关系**：纯前端增量，不触碰后端契约；令牌化后协同编辑、检索等既有视图零行为变更。

**验收要点**：亮/暗双主题下品牌色与排版正确渲染；`npm run typecheck` + `npm run lint` + `npm run build` 通过。

> ⚠ 规范详述应沉淀为 `design-docs/09-design-system.md`（设计侧产出）。本路线图仅引用其结论；该文档当前**尚未提交入仓**，详见 §6 风险 R-DOC-09。

### R2 CRDT 实时协同修复（P0 · YS-42 · M1~M2）

**问题**：打开文档后协同状态短暂显示 "Live"（WebSocket 已连接），5 秒后降级为 "Local"。单端编辑可正常 autosave 落库，但多端无法实时同步内容。这是「协同知识库」核心承诺的回归缺陷——当前实际降级为本地编辑。

**根因**（见 YS-42）：前端 `MoraCollabProvider`（`web/src/lib/collab-provider.ts`）走 mora-api 的 `/api/v1/ws/collab/:document_id`，用自定义 JSON 协议发 `sync-step1` 期望 `sync-step2` 响应；但 mora-api 的 Go collab hub（`internal/module/mora/collab/hub.go` + `cmd/mora-api/wiring.go` `serveCollab`）只做 `presence`/`cursor`/`update` 中继，不实现 Yjs CRDT 初始同步。yjs-server（y-websocket on :1234）已运行，但前端不直连它，Go hub 也未桥接。

**修复方向（供技术评审）**：
- **方案 A（推荐）**：Go hub 实现 sync-step1/step2，Go 侧管理 Yjs CRDT 状态（需引入 Go Yjs 库或自实现同步协议）。
- **方案 B**：前端直连 yjs-server 做 CRDT 同步，Go hub 仅做 presence/cursor（需 nginx 增加 yjs-server WebSocket 代理 + 前端改用标准 y-websocket 协议）。
- **方案 C**：Go hub 将 sync-step1/step2 转发给 yjs-server（Go hub 作 proxy）。

> 三方案均涉及协同链路架构调整，标注为「需技术评审」。方案选择影响 R4 通知的 WebSocket 复用方式，需在 M2 评审时一并确认。

**与 Mora 现有能力的关系**：MVP 已交付「并发降级保底」（YS-34，单文档超 `COLLAB_MAX_CONCURRENT` 自动降级为一人编辑他人只读）与 yjs-server 容器（YS-38）。R2 是在保底之上恢复真协同，不改降级策略本身。

**验收要点**：多端（≥2）打开同一文档一端编辑另一端实时显示；光标/在线状态多端可见；断线重连自动恢复；协同状态持续 "Live" 不降级。

### R3 文档导入与模板（P1 · YS-59 · M3）

**问题**：Mora 当前只能逐篇手建文档，存量知识迁入门槛高；缺乏模板，重复结构（会议纪要/技术设计/周报/API 文档）需每次从头排版。

**目标**：支持从外部批量导入文档，提供常用模板加速创建，降低存量迁移与日常创建摩擦。

**范围**：
1. Markdown 批量导入：上传 `.md` 文件/文件夹，走现有 `content` 包 `MarkdownToBlocks` 解析为 Block 文档，保留标题层级与代码块；目录结构映射为目录树。
2. PDF 导入：PDF 文本提取转 Block（图片/表格降级为附件，标注「尽力还原」）。
3. Docx 导入：Word 结构化转换（标题/列表/表格/图片），评估 pandoc / mammoth 等。
4. HTML 导入：粘贴/上传 HTML，清洗后转 Block。
5. 文档模板：内置模板（会议纪要 / 技术设计 / 周报 / API 文档 / 空白），支持自定义模板保存与复用。
6. 导入文档自动触发 RAG 索引（复用现有 Valkey Streams 事件驱动，`index_status` 流转正常）。

**与 Mora 现有能力的关系**：
- Markdown 导入**直接复用** `content` 包的双向可逆转换能力（往返不丢信息是 Mora 的核心承诺），是技术匹配度最高、应最先交付的入口。
- 导入产出的 Block 文档与手建文档等价，自动进入版本管理与 RBAC 体系，无需新增权限模型。
- 触发 RAG 索引复用现有 `doc_event` → rag-worker 链路，无新增基础设施。

**验收要点**：Markdown 导入保留标题层级与代码块；PDF/Docx 正文可读、结构基本保留；模板可选用与自定义保存；导入文档 RAG `index_status` 流转正常；前端 lint/typecheck/build 通过。

**建议节奏**：M3 内 Markdown 先行，PDF/Docx 后续迭代补齐。

### R4 首页仪表盘与通知机制（P1 · YS-60 · M3~M4）

**问题**：登录后落在空欢迎页，看不到内容概览；关键事件（@提及/权限变更/文档被编辑）无触达，协作闭环不完整。

**目标**：登录即见有价值的内容概览；关键事件有通知触达。

**范围**：

*首页仪表盘（M3）*
1. 最近编辑文档（快速续写）。
2. 收藏/置顶文档。
3. 工作区动态（最近创建/更新/评论）。
4. 索引状态概览（RAG 索引进度/失败数）。
5. 快捷操作（新建文档 / 搜索 / 导入）。
6. 登录后默认路由从空欢迎页改为首页仪表盘。

*通知机制（M4）*
1. 评论 @提及通知。
2. 权限变更通知。
3. 文档被编辑/共享通知。
4. 通知中心（铃铛 + 未读计数 + 列表）。
5. WebSocket 实时推送 + 历史通知查询 API。

**与 Mora 现有能力的关系**：
- 仪表盘的「最近文档/动态/索引状态」均基于现有 mora-api 数据（文档、版本、评论、`index-status`），是读侧聚合，无需新数据模型。
- 通知的 WebSocket 推送**需与 R2 协同链路评审协同**：若 R2 选方案 B（前端直连 yjs-server），通知推送仍走 mora-api 的 WebSocket；若复用 Go hub，需在 hub 内增加通知消息类型。属「需技术评审」的衔接点。
- @提及需在评论正文解析 `@用户名`，与现有评论功能（`/api/v1/documents/:id/comments` + resolve）联动。

**数据模型建议（增量）**：新增 `notifications` 表（user_id / type / target_doc_id / actor_id / read_at / created_at），按 user_id 索引；复用审计日志的追加写模式但不混表。**需技术评审**确认是否复用分区表策略。

**验收要点**：登录默认进入仪表盘展示最近文档与动态；@提及/权限变更产生通知且铃铛有未读计数；通知可标记已读/清除；WebSocket 实时推送生效。

### R5 标签系统与移动端适配（P1 · YS-61 · M4）

**问题**：检索缺少标签维度，跨目录归类弱；移动端仅只读可用，查阅与轻编辑体验缺失。

**目标**：补齐检索标签维度；移动端可查阅与简易编辑。

**范围**：

*标签系统*
1. 文档打标签（多标签），目录树/检索按标签筛选。
2. 工作区级标签管理（创建/合并/删除）。
3. 标签云/热门标签入口。

*移动端适配*
1. 响应式布局打磨（侧栏抽屉、编辑器只读优化）。
2. 触摸交互优化（长按、滑动）。
3. 移动端检索 + 阅读 + 评论可用；编辑降级为简易 Markdown 模式。

**与 Mora 现有能力的关系**：
- 标签是检索的新维度，需进入现有 `search.Filter.Build`（BM25 + 多维筛选 + RBAC 硬过滤）的筛选条件；**RBAC 硬过滤不变**——无权文档的标签同样不泄露。
- 标签与目录是正交的两种组织方式：目录是层级（ltree path），标签是平面多对多。建议标签作 `documents` 的多对多关联表，不侵入 ltree 路径模型。
- 移动端「编辑降级为简易 Markdown 模式」与 MVP 的协同降级策略理念一致：能力不足时优雅降级而非崩溃。

**数据模型建议（增量）**：`tags`（workspace_id / name / slug）+ `document_tags`（document_id / tag_id）多对多；检索 filter 增 `tag_ids` 参数。**需技术评审**确认标签是否纳入 FTS 索引或仅作元数据过滤。

**验收要点**：文档可打标签，检索支持标签筛选；移动端（375px 宽）布局不溢出、阅读/检索可用、编辑至少 Markdown 模式可用；lint/typecheck/build 通过。

### R6 外部分享与协作（P2 · 待规划 · M5+）

**问题**：当前 Mora 面向工作空间内部成员，无法向组织外人员分享单篇文档或邀请外部协作者。

**目标**：支持受控的外部分享与协作，不破坏工作空间隔离与 RBAC 模型。

**范围（待 M4 后细化）**：
1. 单文档外部分享链接（带有效期/访问密码/权限粒度：只读或评论）。
2. 外部协作者邀请（邮箱邀请，独立于工作空间成员）。
3. 分享文档的审计与撤销。

**与 Mora 现有能力的关系**：
- 外部分享**不打破 RBAC**：分享链接本质是「为外部主体生成一条显式权限记录」，决策仍走 `rbac.Engine`（显式允许）。无权资源存在性不泄露的原则对分享链接同样成立。
- 外部协作者需引入「非工作空间成员的用户主体」概念，是对现有 User/Workspace 成员模型的扩展——**需技术评审**。
- 通知（R4）复用：分享事件触发通知。

**风险**：外部分享是私有化部署的安全边界敏感点，需与 `07-security-observability.md` 的安全设计对齐，防止越权与存在性泄露。M5 评审时单独做安全评审。

### R7 AI 写作助手（P2 · 待规划 · M6+）

**问题**：Mora 已有面向 Agent 的 MCP 工具层与 RAG 检索能力，但用户侧无 AI 辅助写作/总结/问答入口。

**目标**：复用现有 RAG / MCP 后端，为用户提供文档内的 AI 写作辅助（续写/总结/改写）与基于知识库的问答。

**范围（待 M5 后细化）**：
1. 文档内 AI 辅助：选中内容续写/总结/改写/翻译。
2. 知识库问答：基于当前工作空间可见文档的 RAG 问答（复用 BM25 + 向量 RRF 融合）。
3. AI 生成内容以 Block 形式插入，受版本管理。

**与 Mora 现有能力的关系**：
- **核心复用**：RAG 检索（`rag/search` RRF 融合 + RBAC 硬过滤）与 MCP 工具层（受 RBAC + 速率限制约束）已是现成后端，AI 助手是其在用户侧的展现，**避免重复建设**。
- RBAC 硬约束不变：AI 问答的召回范围 = 当前用户可见范围，未授权文档不进入上下文、不泄露存在性。
- 私有化不变：推理优先复用本地 TEI/Ollama；若引入 LLM 生成能力，需评估是否出网——**默认不出网**原则下优先支持本地/自托管 LLM 端点，出网选项需显式配置。**需技术评审**。

**风险**：LLM 推理资源占用与延迟；生成内容的版本管理策略；与 R8 画板的 AI 能力边界划分。

---

### R8 画板 / 白板嵌入（P2 · 待规划 · M6+）

**问题**：文档以块级文本为主，缺乏手绘/流程图/白板等可视化表达。

**目标**：在文档中嵌入画板/白板 Block，支持手绘、流程图、便签等可视化协作。

**范围（待 M5 后细化）**：
1. 画板 Block 类型（与现有文本/代码/引用 Block 并列）。
2. 画板协同编辑（复用 Yjs CRDT，与 R2 协同链路一致）。
3. 基础图形工具（矩形/箭头/文本/便签/手绘）。

**与 Mora 现有能力的关系**：
- 画板 Block 是 Block 模型的扩展，需保证 Markdown 双向可逆承诺——画板内容在 Markdown 中如何降级表示（如导出为图片附件 + 摘要）**需技术评审**，不能破坏「往返不丢信息」。
- 协同复用 R2 修复后的 CRDT 链路；R2 是 R8 的前置依赖。

**风险**：Block 双向可逆约束下画板内容的可逆表示；画板协同的性能与并发上限。

采用 RICE（Reach × Impact × Confidence ÷ Effort）做相对排序，分值为 PM 评估的相对值（非实测指标），用于解释排序理由：

| R1 设计语言 | 高（全体用户） | 中（体验基线，非功能阻塞） | 高（诊断清晰） | 低~中 | 次高 | 令牌化为后续迭代铺路，effort 低 |
| R3 导入与模板 | 中（迁移期用户） | 高（降低迁入门槛） | 中（PDF/Docx 有不确定性） | 中 | 中高 | Markdown 先行降低 effort |
| R4 仪表盘+通知 | 高（全体用户） | 高（首次体验+协作闭环） | 中（通知 WS 需评审） | 中 | 中高 | 通知部分依赖 R2 评审结论 |
| R5 标签+移动端 | 中（移动端/重度组织用户） | 中（检索维度+移动可用） | 中 | 中 | 中 | 与 R4 并列 M4 |
